# 部署与配置总览（改代码前必读）

> 本文件是"改一次代码 → 同步更新阿里云后端 + Vercel 前端"的操作手册。
> 记录了全部**地址、别名、部署命令、环境变量清单**。密钥值不写在此文件里（在 `.env` / FC 控制台 / Vercel env 中），这里只列 **key 名 + 用途 + 存放位置**。
>
> 最后更新：2026-08-03

---

## 0. 一句话架构

```
浏览器
  │
  ├── 静态前端(dist/)  ──────────────►  Vercel（只托管前端，不跑任何 API）
  │        │ 构建时 VITE_API_BASE 烘入 FC 地址，浏览器直连后端
  │        ▼
  └── /api/*  ───────────────────────►  阿里云 FC「主服务」 stock-dashboard
                                              （server.js 一个进程托管 dist + api/*.js 12个接口，含 SSE 流式）
                                                │
                                                ├── 数据读写 ──► 阿里云 OSS（替代 Vercel Blob）
                                                ├── 大模型   ──► LLM_BASE_URL（原样，未迁百炼）
                                                └── 量化打分 ──► 阿里云 FC「量化微服务」 quant-score（FastAPI 容器镜像）
```

- **前端**：Vercel 静态托管。构建时把 `VITE_API_BASE` 注入为 FC 主服务地址，浏览器**直连** FC（不走 Vercel 反代，因为 Vercel 外部 rewrite 对 SSE 流式不稳定）。
- **后端主服务**：阿里云 FC 3.0 自定义运行时（`custom.debian10`，`node server.js`）。同一进程既托管 `dist/` 静态前端，又处理 `/api/*` 的 12 个 handler。
- **量化微服务**：独立的第二个 FC 函数（容器镜像 / FastAPI），主服务通过 `QUANT_URL` 调它。
- **存储**：阿里云 OSS，key 前缀 `accounts/` `sectorflow/` `dailyreport/`（与原 Vercel Blob 前缀一致，迁移后直接可读）。
- **大模型**：保持原 `LLM_BASE_URL` / `LLM_API_KEY`，未迁移。

| `OSS_ENDPOINT` `OSS_PUBLIC_BASE` | OSS 可选（同区内网 endpoint / CDN 读取基址） |

## 4. 改代码后的标准操作流程 ★

判断改的是哪一层，对应部署。多数功能改动会同时涉及前后端。

### A. 只改了前端（src/ 下，UI/交互/前端逻辑）
```bash
cd stock-dashboard
export VC_TOKEN="<Vercel Token>"       # 见第 6 节，勿明文打印
export PATH="$HOME/.npm-global/bin:$PATH"
npx vercel deploy --prod --yes --scope natmatthias172-6311s-projects --token="$VC_TOKEN"
# 校验
curl -s -o /dev/null -w "%{http_code}\n" https://stock-dashboard.vercel.app/   # 期望 200
```
> Vercel 会在云端 `npm run build`，自动读取已配置的 `VITE_API_BASE`，把 FC 地址烘进 bundle。

### B. 只改了后端主服务（api/ 或 server.js）
```bash
cd stock-dashboard
npm run build                          # server.js 也托管 dist/，一起打进 FC
set -a; source .env; set +a            # 注入所有环境变量给 s.yaml 的 ${env(...)}
export PATH="$HOME/.npm-global/bin:$PATH"
s deploy                               # 部署 FC 主服务(access=default)
# 校验
curl -i https://stock-dashboard-znrlekbzit.cn-hangzhou.fcapp.run/__health          # 期望 200 ok
curl -s "https://stock-dashboard-znrlekbzit.cn-hangzhou.fcapp.run/api/sectors?type=industry&sort=main" | head -c 200
```

### C. 前后端都改了（最常见）
先做 B（部署 FC 后端），再做 A（部署 Vercel 前端）。两者独立，顺序不强制，但后端先上可避免前端调到旧接口。

### D. 改了量化微服务（qlib-service/）
量化服务已改为 **FC3.0 免 Docker 自定义运行时**（`custom.debian10`），依赖以 linux cp310 wheel 形式 vendored 到 `deploy_pkg/deps/`（约 300M，已 gitignore，用脚本重建）。**本沙箱无 Docker，容器方案不可用，一律走此路径。**

```bash
cd stock-dashboard/qlib-service
# 1) 若改了依赖(requirements)或首次重建部署包:
bash build_deploy_pkg.sh                # 重新 vendor 依赖 + 拷源码/模型到 deploy_pkg/
# 若只改了 app.py/model_lib.py/factors_lib.py,不必重跑上面,直接同步源码即可:
cp app.py factors_lib.py model_lib.py lgb_score.txt meta.json bootstrap deploy_pkg/

# 2) 部署(只更新函数代码/配置,不动既有 http 触发器与 URL):
set -a; source ../.env; set +a
export PATH="$HOME/.npm-global/bin:$PATH"
s deploy -y

# 3) 校验(冷启动首次可能几秒,重试到 ver=3.0-lgb-garch):
curl -s https://quant-score-nlxgclpdbu.cn-hangzhou.fcapp.run/health          # {"ok":true,"ver":"3.0-lgb-garch"}
curl -s https://quant-score-nlxgclpdbu.cn-hangzhou.fcapp.run/model_info -H "X-API-Key: $QUANT_KEY"  # {"loaded":true,...}
# POST /predict 传 candles 应返回 engine=lgb + forecast.volEngine=garch
```

> **模型加载策略**：`model_lib` 优先用**部署包内 bundled 模型**(离线永远可用),OSS 上的 `quantmodel/lgb_score.txt` 仅作**热更新**——训练出新模型后 `upload_model.py` 推到 OSS,进程 TTL(1h)到期自动拉取覆盖。两者都失败才回落规则打分,**服务永不崩**。
> **重训模型**：`python3 build_dataset.py --pool 600 --bars 700 --out dataset.npz` → `python3 train_lgb.py` → 把新 `lgb_score.txt`/`meta.json` `cp` 进 `deploy_pkg/` 重部署(或 `upload_model.py` 走 OSS 热更新)。当前:36因子(Alpha158风格,纯numpy),179407样本,5折时序CV AUC≈0.606(旧11因子基线0.593);顶部重要度 amp20/wr14/cci14/atr_pct 多为新增因子。**因子只做加法**——原11个键与内部字段(_atr/_ma20/_last/_rets)保留,app.py 规则兜底依赖。
> **触发器坑**：线上函数已有一个 http 触发器(名字非 `http`)。s.yaml **故意不声明 triggers**,否则 fc3 会尝试再建一个触发 `LimitExceededError`(一个函数只能有一个 http 触发器)。URL 保持不变。

## 5. 部署要点/踩坑（务必遵守）

1. **Vercel 只上前端**：`.vercelignore` 已排除 `api/ server.js s.yaml .env` 等。绝不能让 `api/*.js` 被 Vercel 当 Serverless Function（会触发 Hobby 版 12 函数上限，也会抢在直连之前拦 `/api/*`）。
2. **前端直连 FC，不走 Vercel 反代**：因为 SSE 流式（AI 逐字输出）在 Vercel 外部 rewrite 下不稳定。靠 `VITE_API_BASE` 直连 + 后端 CORS `Access-Control-Allow-Origin *`。
3. **FC 只上运行所需**：`.fcignore` 排除 `src/ docs/ scripts/ *.tar.gz` 等；但会上传 `dist/ api/ server.js node_modules package.json`。所以**部署 FC 前必须先 `npm run build`**。
4. **改 FC 地址要联动**：只要 FC 函数被删除重建导致地址变，必须同步：① Vercel `VITE_API_BASE`；② `.env` 的 `QUANT_URL`（若变的是量化服务）；③ 本文件第 1 节。
5. **Deployment Protection(SSO)**：Vercel 项目此前已关闭（公开可访问返回 200）。只需关一次，后续部署不会重新开启。
6. **密钥安全**：Token/AK/SK 只存环境变量与 `.env`（`.env` 已在 `.gitignore`），绝不写进代码、日志、提交、或本文件。
