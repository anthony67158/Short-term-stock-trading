# 设计理念与产品逻辑

> 本文讲清「短线操盘台」为什么这样设计、每个模块解决什么问题、数据与 AI 如何流动。配合根目录 [README](../README.md) 阅读。
>
> 本文同时是前端组件的设计基线。新增或改造任何用户界面时，必须遵守第六节，不得为单个功能另起一套视觉语言。

---

## 一、一句话定位

把散户的痛点——**「看得懂行情，却做不出决策；有纪律，却守不住」**——用一条闭环解决：

```
选股  →  建仓 / 做T  →  盯盘预警  →  仓位纪律  →  交易复盘
 ▲                                                      │
 └──────────────── 复盘反哺下一次选股 ───────────────────┘
```

它不是又一个行情看板，而是一个**决策 + 纪律 + 复盘**的工作台。**刻意不做真实下单**——下单留在券商 App，本平台专注「想清楚、守得住、复得了盘」。

---

## 二、四条设计原则

1. **从「看」到「驱动决策」**
   看板是被动的（我去看），操盘台是主动的（它提醒我、约束我）。所以有了**盯盘预警**（命中即通知+响铃）、**策略信号灯**（自动判定买卖）、**交易计划**（触及止盈止损即报警）。

2. **AI 不说空话：数据 + 理论双支撑**
   每个 AI 结论都建立在两根支柱上——**实时数据**（行情/资金/分时/量价）+ **经典理论**（道氏/缠论/龙头战法/量价，RAG 召回并标注引用）。宁可给"观望"，不给没依据的"买"。

3. **纪律可执行、可监控**
   把交易法则**代码化**：「踏5不破10」变成信号灯规则引擎、8% 止损变成硬约束、止盈止损变成到价预警。规则跑在盘中，而不是停在脑子里。

4. **真实、不失真**
   价格**原样显示、绝不四舍五入**（"上下浮动一点都是很多钱"）；成本/浮盈一律**含费口径**（佣金+印花税+过户费）；做 T 用 **FIFO 配对**算真实差价。

## 三、模块设计逻辑（为什么这么分）

按**操盘的时间顺序**组织导航，而不是按功能堆砌：

| Tab | 对应操盘阶段 | 核心设计意图 |
|---|---|---|
| **今日决策** | 盘前研判 + 选股 | 先答「今天能不能做」（情绪温度计+市场纪律），再答「做什么」（板块前瞻、公式选股和候选池）。避免开盘就冲动。 |
| **持仓执行** | 建仓 / 盘中操作 | 交易闭环主战场：建仓→做T摊薄→减/清仓。每只持仓挂**策略信号**（该拿还是该走）+ **交易计划**（止盈止损）。 |
| **账户闭环** | 仓位纪律 + 复盘 | 三合一：账户全景（我有多少、仓位多重）、盯盘预警（帮我盯）、交易记录（我做得怎样，绩效归因）。 |
| **盘面研究** | 全局环境 | 大盘资金流向、板块轮动、成分股下钻——判断"顺风还是逆风"。 |

**关键取舍**：账户全景、盯盘预警、交易记录三者本质都是"我的账户"的不同视角（有多少钱→盯什么→做过什么），所以合并成一个 Tab 用子页切换，而非三个平级入口——减少认知负担。

## 四、AI 能力分层

三层协作，各司其职，避免"大模型什么都干"：

```
┌─────────────────────────────────────────────┐
│  ① 工具增强 Agent（Function Calling）          │  开放问答：自主多轮调用
│     行情/选股/资金/涨停/异动/情绪/新闻工具      │  工具后综合作答
├─────────────────────────────────────────────┤
│  ② 结构化 AI（JSON 模式）                      │  确定任务：今日操盘 /
│     今日操盘·盘面复盘·做T建议·交易计划定价      │  做T建议 / 计划定价
├─────────────────────────────────────────────┤
│  ③ 本地规则引擎（不调 LLM）                     │  实时、零延迟、零成本：
│     「踏5不破10」信号灯·止损纪律·均线技术结论    │  盘中即时判定
└─────────────────────────────────────────────┘
        ▲                    ▲
        │   RAG 知识库（BGE-m3 向量检索）         │
        │   道氏/缠论/龙头战法/量价/情绪周期/风控   │  给 ①② 注入理论依据
        └────────────────────────────────────────┘
```

- **能实时算的绝不调 LLM**（信号灯、均线、止损）→ 快、免费、盘中可靠。
- **需要判断和表达的用 LLM**（选股逻辑、计划定价、盘面解读）→ 有据可依、标注引用。
- **AI 定价交易计划**：LLM 结合 MA5/10/20、近20日支撑压力、当日 VWAP、量价、持仓成本，给出止盈/止损价 + **定价依据**，用户可改——降低"不懂技术无从下手"的门槛。

## 五、数据流

```
东方财富等公开接口 ──(多镜像容错)──> 阿里云 FC 单进程 API
        │                                  │
        ├── 行情/K线/分时/资金/涨停/异动     ├── LLM / RAG / 量化服务
        │                                  └── OSS 权威账本与任务状态
        ▼
   React UI（Vercel + FC 双入口，同一前端版本）
        │
        ├── 交易时段行情轮询与到价快路径
        └── 本地规则反馈 + 云端确定性任务进度
```

**为什么前端做预警判定**：预警要盯几十只票、秒级响应，放服务端会烧函数额度且有延迟；前端轮询报价 + 本地判定命中，既省成本又即时。

## 六、界面设计基线

### 6.1 设计方向

界面采用 **Apple 的空间秩序与即时反馈**，结合 **Google Material 的状态清晰度和可访问性**，最终服务于高密度交易工作台，而不是复刻任何消费级系统。

- **安静、可信、直接**：先显示结论和动作，再显示价格、依据与高级细节。
- **熟悉且可预测**：相同外观的控件必须有相同行为；刷新、展开、返回等操作固定使用统一图标。
- **即时反馈**：点击后立即进入按压或运行状态。超过一秒的任务必须说明正在做什么；多阶段任务必须展示服务端真实进度，禁止用循环动画伪造完成度。
- **克制的动效**：只使用 `transform` 和 `opacity` 提供短反馈；普通界面不弹跳、不延迟输入，并支持 `prefers-reduced-motion`。

### 6.2 表面与层级

- **单层表面**：一个业务模块只使用一个主容器。禁止卡片套卡片，也禁止用多个相邻大卡重复标题。
- **层级靠排版与间距建立**：标题、结论、指标和证据通过字重、留白、弱底色与单条分隔线组织，不依赖连续边框。
- **指标使用连续信息带**：同组价格或指标共享一个弱底色容器，内部仅用细分隔线；不得把每个数字做成独立悬浮卡。
- **边线只表达真实边界**：列表行、滚动层和必要的表格列可使用细线；卡片内部的标题、指标、证据和操作优先通过留白与弱底色分组，禁止连续横线、竖线把内容切成表格。
- **卡片按内容状态对齐**：桌面端仅对已生成建议的卡片做同一网格行等高，差额留在证据与底部操作之间；未生成建议的卡片保持自然高度，禁止为对齐制造空白。移动端全部恢复自然高度。
- **置顶状态必须可辨识**：自选置顶同时使用浅蓝表面、整圈蓝色边框和强化星标；不使用顶部色条，也不得只依赖颜色表达。
- **浮层才使用深度**：抽屉、对话框和系统通知可使用阴影或半透明材质；普通页面区块不使用装饰阴影。
- 面板、控件、输入框只使用 `tokens.css` 中的圆角、颜色、间距和阴影变量，禁止新增未经体系定义的视觉常量。

### 6.3 信息层级

每个决策模块按固定顺序组织：

1. **标题与唯一主操作**：同一行、固定位置；图标按钮必须有 `aria-label` 和悬停说明。
2. **当前结论**：用一句白话明确“现在做什么”，不能先堆指标。
3. **关键价格或指标**：价格使用等宽数字和 `tabular-nums`，同组基线对齐。
4. **证据与限制**：用短行呈现，可折叠的高级内容放到下一层。
5. **状态与时间**：明确数据时点、保存结果、失败原因和下一步。

用户界面不得直接暴露内部枚举、字段名或公式代码，例如 `CLOSE_TREND_PULLBACK`、`RISK_OFF`；必须翻译为普通中文。

### 6.4 颜色与文字

- **A 股语义色固定为红涨绿跌**：红表示上涨、买入、流入；绿表示下跌、卖出、流出。
- 钴蓝只表示当前选择、可交互入口和中性进度；黄色表示等待或需确认；危险红仅用于错误和硬风险。
- 颜色不能单独表达状态，必须同时有文字、图标或形状。
- 正文使用系统兼容无衬线字体，价格、金额、百分比使用等宽字体。
- 所有组件 `letter-spacing: 0`，不随视口缩放字号；紧凑面板使用小而清晰的标题，不使用营销式大标题。

### 6.5 控件、反馈与任务进度

- 图标统一复用 `src/components/Icon.jsx`；熟悉动作优先用图标，文字按钮只用于明确命令。
- 二元设置使用开关或复选框，视图切换使用分段页签，数值输入使用输入框或步进控件。
- 同一工具栏或操作组内的按钮、分段控件、选择器必须共享同一个高度 token，不能依靠各自 padding 撑出近似高度。
- 纯图标按钮必须由同一个尺寸变量同时约束宽、高和最小宽高，并设置 `aspect-ratio: 1`；禁止出现 `36×40`、`40×44` 等瘦高或扁宽形态。
- 所有交互在按下时立即反馈，运行按钮使用 `aria-busy`，不可重复提交时必须禁用。
- 状态分为四类：**进行中、完成、警告、错误**。错误必须说明原因，空态必须说明当前结论。
- 长任务进度必须来自服务端权威阶段，至少展示“当前阶段、完成比例、步骤序列”；刷新或换设备后仍能恢复，失败和超时不能长期伪装成运行中。
- 加载状态应保持稳定尺寸，避免按钮、标题和内容跳动；内容加载优先使用骨架或阶段状态，不使用无上下文的独立转圈。

### 6.6 响应式与可访问性

- 桌面优先保证扫描效率，移动端优先保证单手操作；固定格式元素必须定义稳定网格或尺寸。
- 至少验收 `320px`、`768px`、`1024px` 和 `1440px`，不得出现横向页面溢出、文字遮挡或按钮被压缩。
- 触屏目标最小 `44px`；桌面紧凑控件可为 `40px`，但需保留明确焦点态。
- 所有交互元素必须可键盘访问；动态状态使用 `aria-live`，进度使用 `role="progressbar"`，不能只靠颜色传达。
- 支持 `prefers-reduced-motion` 与 `prefers-reduced-transparency`；减少动效时保留状态变化，不保留弹跳和位移。

### 6.7 交付检查

任何新增或改造的前端组件在合并前必须确认：

- 与相邻模块共用同一标题、边界、间距和控件语言。
- 加载、成功、空数据、错误、禁用状态完整。
- 白天和夜间主题均可读，A 股红绿语义正确。
- 桌面和移动端均无溢出，按钮文字不被裁切。
- 浏览器控制台无新增错误，关键接口状态正常。
- 影响 `dist/` 的修改已同步部署到 Vercel 与阿里云 FC。

## 七、技术边界（诚实声明）

- **不做真实下单**：个人对接券商下单不合规、也无公开接口。定位就是决策工具。
- **数据仅 Level-1（免费）**：分时、五档可取；Level-2 逐笔/千档拿不到，涉及主力逐笔的功能用 Level-1 近似，不过度承诺。
- **AI 与规则均为参考**：所有信号、定价、结论**仅供研究，非投资建议**。
