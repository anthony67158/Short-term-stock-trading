## 0. 执行摘要

将平台重新定义为：**面向个人投资者的 A 股研究、选股、组合决策与策略验证工作台**。

用户在一个平台完成六件事：理解市场、研究股票、发现机会、管理持仓、记录执行、验证与改进策略。模型、公式、规则和 Agent 是实现这些任务的内部能力；产品围绕投资任务组织，不围绕模型名称和历史功能堆页面。

**已确认的核心要求：量化模型与 Agent 服务必须共同参与整个系统，尤其是选股与持仓管理。** Agent 参与事件研判、投资论点、反证、策略适配和持仓逻辑变化，量化模型参与排序、概率、收益分布和动作价值估计；两者在决策发布前汇合。公式只承担特征计算、约束和执行，不构成独立替代这套协作的生产决策系统。

采取**新内核、新数据模型、新 API、新界面、新测试体系**的整体重建。旧实现不作为新系统的依赖；旧规则不因曾经写入文档就自动生效。保留可用的环境资产、数据访问能力与经过核验的真实交易事实，旧业务代码、历史设计文档和测试代码在重建阶段按清单退出当前开发树。

推荐技术路线：**React + TypeScript 前端、Python/FastAPI 模块化后端、PostgreSQL 业务数据库、OSS 数据与模型仓库、独立任务进程**。在线决策和历史回测调用同一个 Python 领域内核，避免长期维护 JS/Python 两套交易计算。

UI 参考 **Linear 应用本身**的稳定侧栏、紧凑列表、上下文详情、键盘操作、克制色彩与清晰状态；不使用营销首页的装饰风格组织交易工作台。

完整交付不以“页面能打开”作为结束：必须能沿着“证据 → 策略 → 决策 → 人工成交 → 归因 → 实验 → 发布”追踪任意一次决策。

## 2. 问题定义

### 2.1 真正要解决的问题

当前系统缺少围绕完整投资过程的一致产品模型。能力不断叠加后，选股结果、股票研究、交易建议、持仓账本、预警状态与训练目标相互牵连，修改一个环节容易引入新的兼容分支。用户难以确认“现在该做什么、依据是什么、执行后怎么验证”。

重建要同时消除两类问题：

1. **产品问题**：围绕历史功能名称组织入口，用户任务与最终决策之间缺少稳定关系。
2. **工程问题**：事实存储、决策计算、显示修正和异步恢复混在一起；前后端重复承担业务判断，文档与实现口径长期漂移。

单纯拆文件、改主题或替换模型，无法解决这两类问题。

### 2.2 目标状态

每天开盘前看到有依据的关注方向与计划；盘中知道哪些机会值得研究、哪些持仓需要动作；成交后账户立即准确更新；盘后能解释盈亏来自策略、市场还是执行；研究发现能变成可重复的策略实验，合格实验能成为唯一生产版本。

“完整”是任务闭环完整，不是一次性装下所有数据、所有策略和所有金融品种。

## 3. 产品目标与非目标

### 3.1 产品目标

| ID | 目标 | 可观察结果 |
|---|---|---|
| G01 | 建立统一投资工作流 | 机会可关联研究、决策、成交和复盘 |
| G02 | 提高有效选股与研究效率 | 来源清楚、过滤可复用、同股不重复研究 |
| G03 | 在账户约束内形成明确决策 | 每只股票一个当前有效动作，数量、价格条件、有效期齐全 |
| G04 | 提高策略的费后风险调整收益 | 同口径回测、基准比较、压力测试和实盘归因可核查 |
| G05 | 建立可持续策略迭代 | 每个生产策略可追溯数据、公式、模型、评估和发布版本 |
| G06 | 降低维护复杂度 | 单一事实源、单一决策内核、明确依赖方向、无永久旧链路 |

### 3.2 非目标

- 首版不连接券商自动下单；采用系统决策、用户实际交易、人工或文件导入成交的模式。
- 不承诺收益率或胜率；工程可验证，盈利能力必须由样本外与实际执行结果证明。
- 不建设高频交易、逐笔盘口交易、融资融券、衍生品、多市场交易和对外资管系统。
- 不创建无限协作的“多 Agent 投资委员会”；复杂度必须对应可衡量的增益。
- 不在首版引入 Kubernetes、Kafka、独立知识图谱库、向量数据库集群或通用工作流画布。
- 不保留旧页面和旧接口作为永久兼容层；旧研究资料也不参与新生产决策。

## 4. 核心约束、假设与不变量

### 4.1 可重新选择的内容

旧 UI、旧 JS 计算层、旧 OSS 账户快照设计、旧模型维度、旧固定规则、旧端点槽位和旧部署习惯均可替换。公式数量、策略数量、复核窗口、概率阈值、股票召回方式都应成为有依据的版本配置。

### 4.2 仍需保持的事实语义

这些要求来自新系统的正确性，而非旧架构惯例：

- 用户确认计划不代表券商成交；只有真实成交改变真实持仓。
- T+1、证券交易单位、停牌、价格限制、实际费用按证券及生效时间执行。
- 行情、财报、新闻都有可用时间；未来数据不能进入历史决策。
- 真实成交、模拟成交、模型预测、研究观点分别存储和展示。
- 代码清理不等于删除真实账户、云端数据、密钥或域名。
- 新旧系统不能同时写同一账户事实。
- 外部文本及 Agent 不能改写用户风险授权、账本或生产版本。

### 4.3 设计假设

首期个人使用，保留少量多账户能力；全 A 股可搜索研究，交易支持按板块能力逐步启用；桌面工作台优先，移动端支持查看、提醒和成交录入。投资周期覆盖短线、波段和中期研究，但首个可验收策略采用明确的单一周期，再扩展其他周期。

技术容量初值：1～5 个使用者、最多 10 个投资账户、100 只重点监控股票、全市场收盘批量研究与扫描。超出范围先做实测，再扩容。

## 6. 用户场景与产品设计

一级工作区统一为：

| 工作区 | 核心问题 | 主要产物 |
|---|---|---|
| 今日工作台 | 今天我最需要处理什么？ | 待处理事项、市场摘要、账户风险、当日计划 |
| 市场与选股 | 现在有哪些值得进一步判断的标的？ | 扫描运行、候选池、保存的筛选视图 |
| 股票研究 | 这家公司为何值得关注，论点如何证伪？ | 股票档案、证据、研究论点、事件时间线 |
| 组合与执行 | 我的资金如何配置，当前应怎样处理持仓？ | 组合决策、执行计划、成交与账本 |
| 策略实验室 | 哪种方法在什么条件下有效？ | 策略版本、回测、消融、部署记录 |
| 复盘与洞察 | 盈亏由什么造成，下一步应改什么？ | 策略归因、执行偏差、实验提案 |

通知收件箱和全局搜索属于公共能力，设置属于低频管理入口。Agent 作为各任务内的研究工具和全局任务入口，不额外占据“AI 世界”一级导航。

## 7. 目标架构与职责分配

| 层 | 唯一责任 | 主要实现 |
|---|---|---|
| 交互层 | 展示事实、提交命令、解释状态 | React / TypeScript |
| 应用层 | 身份、API、任务编排、事务、通知 | FastAPI + 应用服务 |
| 领域层 | 账户约束、策略运行、动作比较、组合决策、执行投影 | 纯 Python 内核 |
| 研究计算层 | 特征、标签、模型训练、回测、评估 | Python 作业，复用领域内核 |
| 事实层 | 账户、策略、任务、证据、决策索引与版本 | PostgreSQL |
| 大对象层 | 历史行情、原文、模型包、回放明细 | OSS + Parquet |
| 外部适配层 | 数据供应商、搜索、LLM、通知、云平台 | 受控 Adapter |

业务 API、实时监控与后台作业使用同一代码仓库，运行在隔离进程中。首版不按每个业务模块拆微服务。前端不计算权威仓位、费用、交易合法性或买卖动作。

## 8. 备选方案与决策

### 8.1 重建方式

| 方案 | 最强支持 | 最强反方 | 裁决 |
|---|---|---|---|
| 原地逐模块修补 | 利用现有运行能力，短期交付快 | 容易继续保留双逻辑、历史状态和补丁依赖 | 不作为本次主路线 |
| 新目录重建、数据单向迁移、一次切换 | 边界清晰，旧代码能彻底退出，符合本次诉求 | 早期投入大，需重新证明交易正确性 | 推荐 |
| 立即删除全部再探索需求 | 开发树最干净 | 未提交资产不可恢复，功能目标尚未固化，现有服务维护能力丢失 | 将删除放到有恢复点的新分支阶段 |

新旧运行环境短期并存只服务切换，不意味着新代码依赖旧系统。新平台不能为了接入旧模型重建所有旧字段。

### 8.2 后端选择

保留 TypeScript API + Python 量化可减少短期改写，但容易留下双语言的费用、仓位、规则和回测语义。全部业务转 Python 的代价是重新建设 API、认证和任务基础设施，收益是领域内核天然同源。

本次目标是完整重建，推荐后者。若 Python 在线批量推理无法满足实测延迟，先拆出计算进程和优化热点，不直接再写一套 JS 决策引擎。

### 8.3 策略与 Agent 的地位

量化与 Agent 是共同的核心能力，必须从首个决策闭环进入系统。Agent 的结构化研判可影响候选召回、策略适配、证据状态、事件特征和持仓复核；量化在相同快照下估计收益风险与动作价值；账户决策器综合这些输入，输出唯一建议。Agent 不仅写解释，量化也不仅提供一个装饰性分数。

纯公式、纯量化、纯 Agent 可作为离线消融对照，不作为本平台完整生产形态。必要 Agent 研判缺失或模型不合格时，显示研究或决策能力不足，不悄悄切成纯公式买卖。硬止损提示、交易合法性检查和真实成交记账独立可用。

最强反方是联合系统延迟高且难以归因。因此采用版本化 Agent 研判快照、事件触发更新、联合消融和预算控制；不在每次报价时启动一轮自由讨论。首期实现有限角色和明确工具合同，不建设通用插件商店。

## 9. 优先级与里程碑

| 里程碑 | 用户获得的结果 | 退出条件 | 证据 |
|---|---|---|---|
| M0 重建基线 | 一个清晰、可恢复的新开发起点 | 文档、保留清单、备份与目标合同固定 | 清理清单和恢复验证 |
| M1 研究闭环 | 查股、看行情、收藏、Agent 研究证据可用 | 数据时间与来源可查，研判可追溯，断档明确 | 研究场景端到端证据 |
| M2 账户闭环 | 录入成交、查看真实持仓与风险 | 现金/持仓/T+1/冲正全部对平 | 账本与并发测试 |
| M3 联合决策闭环 | 模型与 Agent 联合选股、持仓评估→计划→成交→复盘 | 两者均实质参与、同一内核回放、异常可恢复 | 完整交易 episode 与消融 |
| M4 实验闭环 | 研究假设能形成可比较实验 | 数据冻结、费用、样本外和失败结果齐全 | 实验与发布报告 |
| M5 持续学习与扩展 | 多周期联合策略、自动实验与版本选择 | 增益可归因，失败不破坏基础系统 | 消融与 Agent 评测 |
| M6 正式切换 | 新平台独立承担日常使用 | 迁移对账、生产验收、旧调度关闭、旧实现清除 | 切换及恢复演练 |

优先保证事实、账户与模型—Agent 联合闭环。更复杂模型与更多 Agent 角色排在闭环可信之后，但不把核心模型与 Agent 推迟成可选增强。具体顺序、并行条件和任务在 06 分册。

## 10. 验收与指标

平台级硬验收：事实账本对平；无未来信息；同一个输入和版本可重放；过期/错版计划不能执行；重复命令不会产生重复成交；一次失败可从任务记录定位原因。

产品级验收：用户从一个候选进入研究、形成计划、记录成交、查看归因，不需要复制股票代码、重抄研究结论或打开另一套建议页面。

收益评估：同时报告费后收益、相对基准、回撤、水下时长、换手、资金利用率、策略容量、分市场阶段表现及统计不确定性。交易次数是覆盖诊断，不是强迫下单的目标。具体发布政策训练前冻结，不能试验失败后调低门槛。

## 11. 风险、迁移与回滚

最大风险并非新 UI 开发，而是历史数据质量、执行模拟失真、账户迁移错误和模型过拟合。对应优先验证数据授权与点时可用性、撮合规则、真实账本和样本外评估。

代码与文档可由归档恢复；生产账户必须单写；新系统发生新成交后回滚应用版本，不能拿旧快照覆盖新账本。旧数据作为隔离历史资产保留，不作为新系统可变事实源。详细方案见 07。

## 12. 开放问题与证据缺口

| 问题 | 默认设计 | 在何阶段必须解决 | 翻转条件 |
|---|---|---|---|
| 行情和财务数据的付费预算 | Adapter 支持更换供应商，先验证日线与基础财务 | M1 前 | 无法合法稳定获取分钟线时限制盘中策略 |
| 生产数据库与常驻计算资源 | 同地域托管 PostgreSQL + 容器进程 | M0 技术验证 | 成本或云能力不满足再选择 FC 常驻形态 |
| 首个生产策略周期 | 短线/波段模板先跑通；中期研究同平台支持 | M3 前 | 用户交易偏好改变时更换模板，不改领域模型 |
| 联合模型是否有可交易增益 | 不预设，M3 建立联合版本与离线消融基线 | M3 / M4 | 不合格则只提供研究与账本，继续改进，不启用纯公式替代 |
| 真实持仓历史是否完整 | 允许有来源的期初仓位，禁止伪造历史成交 | M2 / M6 | 完整交割单可用时补齐并核验 |
| 历史策略发布阈值是否继续适用 | 重新冻结风险与发布政策，不继承旧阈值 | M3 / M4 | 样本和风险偏好决定阈值，而非回测结果 |

这些未知项不阻止 UI、账本、研究和接口骨架设计，但会阻止相关交易能力正式启用。
