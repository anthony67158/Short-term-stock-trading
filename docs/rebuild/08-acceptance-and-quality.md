# 验收与质量体系

> 隶属 `a-share-platform-rebuild.v1.0`。本册规定验收证据，不声称下列测试已实施或通过。

## 1. 五类完成状态

| 状态 | 证据 |
|---|---|
| 设计完成 | 目标、合同、任务、验收与未决事项齐全 |
| 实现完成 | 代码及schema存在，构建成功 |
| 离线验证完成 | 关键业务场景、数据回放和失败路径通过 |
| 部署完成 | 版本、配置和工件实际加载并回读 |
| 生产验收完成 | 真实集成及隔离测试账户的完整路径通过 |

模型训练结束不等于策略合格；接口202不等于研究完成；研究文本显示不等于Agent参与决策；页面200不等于产品验收。

## 2. 核心验收矩阵

| ID | 前提与操作 | 预期用户结果 | 必须检查的后台证据 | 阶段 |
|---|---|---|---|---|
| AC01 研究闭环 | 搜索证券→打开档案→运行研究→保存论点→刷新 | 同一股票档案恢复，研究有引用和版本 | subjectId/assessmentId/thesisRevision一致 | M1 |
| AC02 点时数据 | 给定一条盘后公告，回放当日盘中决策 | 盘中结论不包含该公告 | availableAt截断、输入hash、未来删除前后结果一致 | M1/M3 |
| AC03 数据缺口 | 扫描缺一页/重复证券/旧行情/缺财务 | 清楚显示覆盖缺口，不称全量完成，不造数 | coverage报告与缺失状态进入消费端 | M1/M3 |
| AC04 真实账本 | 入金、买入、次日卖出、费用、分红、冲正 | 现金与持仓逐步正确 | 独立重算、批次、现金分录逐笔对平 | M2 |

| AC10 一次复核 | 同一触发重复报价、断网、重启Worker | 一个episode与明确终态；硬风险提醒继续 | triggerKey唯一、fencingToken、lease/终态审计 | M3 |
| AC11 同源回测 | 固定快照分别调用在线内核和回放入口 | 动作/数量/价格条件一致 | 逐字段金样、同版本费用/模型/研判 | M3/M4 |
| AC12 Agent边界 | 原文含指令注入、伪数值、无来源推断、越权工具 | 伪事实拒绝，推断标记，无法改账本/风险 | tool policy、引用校验、budget与拒绝原因 | M1/M3 |
| AC13 联合失败与冲突 | Agent超时或模型失败；双方明显冲突 | 不冒充READY/HOLD，不暗切纯公式；显示缺口/分歧 | state组合、超时、缓存指纹、被阻断发布 | M3 |
| AC14 实验可信 | 同账户条件比较完整联合及四类对照 | 真实/模拟、成本、覆盖和不确定性齐全 | 冻结split、试验注册、逐笔结果、消融配置 | M4 |
| AC15 发布一致 | 缺工件/加载失败/并发发布/旧Worker完成 | 保留有效包，无混版新决策 | manifest hash、原子指针、inflight版本检查 | M4 |

| AC19 迁移与恢复 | 重复迁移、缺历史、切流后新增成交、回滚 | 事实不丢不重，旧系统不能继续写 | sourceHash、对账、写入水位、恢复演练 | M6 |
| AC20 工程清理 | 检查工作树/构建/路由/定时任务 | 新系统独立运行，无旧决策链 | import边界检查、部署清单、旧任务停用记录 | M6 |

## 3. 测试分层与取舍

### 3.1 领域测试

重点覆盖金额、数量、T+1、费用、预留、动作合法性、触发幂等和时点筛选。使用性质测试检查守恒：

- 买卖与冲正后现金/数量回到可证明状态；
- 可卖量不大于总量，不为负；
- 相同命令重复执行不改变第二次结果；
- 增加未来数据不能改变历史快照计算；
- 无交易时净值变动来自持仓估值或现金事件，不能来自虚构成交。

不为每个低影响排版或机械getter写镜像测试。测试应保护业务合同，不机械断言函数内部实现。

### 3.2 数据库与合同测试

使用真实隔离PostgreSQL验证事务、锁、唯一约束、deadlock重试、fencing和outbox。内存mock不能证明数据库并发正确。

用固定fixtures校验后端DTO、OpenAPI、TS客户端、模型输入输出、Agent产物和事件schema。跨版本兼容有正反样例。

### 3.3 场景回放

建立小型但语义完整的合成案例：停牌、缺页、部分成交、同柱双触发、真实交易变化、Agent反证、模型不可用、旧Worker晚返回。

每个案例保存输入、时间线、预期用户结果和关键账务断言。避免复制整个真实账户作为回归样本。

### 3.4 浏览器

Playwright验证导航、股票切换、任务恢复、成交表单、联合详情、错误状态、收件箱及账户隔离。可见页面必须与后台状态一致。

按钮存在不等于业务闭环；需验证点击产生的命令、服务端状态、刷新后的结果和下游关联。

## 4. 模型评估

| 维度 | 必报项 |
|---|---|
| 成交 | 校准曲线、Brier、不同路径/流动性下误差、部分成交 |
| 收益 | 条件盈利概率、分位数损失、覆盖率、尾部偏差 |
| 排序 | RankIC、分桶收益、Top候选覆盖与交易可行性 |
| 持仓动作 | 相对HOLD增量、动作分布、regret、早退与迟退分组 |
| 组合 | 费后收益、回撤、水下期、换手、集中度、容量 |
| 稳健性 | 时间外窗口、市场阶段、行业、个股集中、压力费用 |
| 不确定性 | 有效样本、时间相关性、置信区间、试验数量 |
| 服务 | 推理时延、内存、缺失特征、分布外比例 |

不得把回测内拟合指标当生产收益证据。净收益必须包含声明的交易成本；LLM/数据/运行成本在平台净价值评估中另列，避免重复扣费。

至少报告基础滑点与更高成本压力场景。10bps可以作为参考压力点之一，但是否代表实际压力需由流动性、订单规模和真实偏差验证。

## 5. Agent评估

建立事件抽取、股票研究、持仓变化、组合关系、复盘与实验提案六类案例。

评分维度：来源真实性、引用支持、数值忠实、时点正确、事实/推断区分、反证完整、工具正确、任务完成、权限合规、成本和时延。

关键失败直接判失败：引用不存在来源、将未来事实用于历史决策、改写真实账户、伪造量化概率、忽略重要反证、任务超时伪报完成。

语义质量可由人工标注与独立评价辅助，不能只让同一个模型自评“正确”。财务数值和API权限由确定性检查验证。

两类验收分开：

1. **功能参与**：Agent产物确实改变了输入、候选、论点状态或复核；
2. **实际增益**：联合系统较去Agent对照在研究质量、风险或收益上有所改善，且成本合理。

强制每个case改变最终动作是不合理的；很多情况下两种输入都应输出相同动作。应检查作用路径与整体增益。

## 6. 联合系统评估

冻结同一数据与预算配置，比较完整联合、去Agent、去量化、公式基线。后面三者仅为对照，不作为本平台默认生产替代。

评估不止平均收益：Agent是否发现新事件机会、是否减少论点失效后的迟退、是否造成不必要恐慌减仓、模型是否过滤叙事型负期望、两者冲突时是否正确等待。

若收益无法统计区分但研究效率有改善，报告为“研究效率增益，交易增益未证实”。不能为了满足联合愿景声称必然更赚钱。

## 7. 发布门禁

发布前冻结具体ReleasePolicy：

- 风险上限、成本压力范围；
- 时间划分与最终确认集；
- 最小有效样本与覆盖要求；
- 置信水平、重采样方法与允许不确定性；
- 模型校准与服务指标；
- Agent关键错误容忍度；
- 对当前冠军的比较口径；
- 完整包加载及回滚要求。

文档不虚构适用于所有策略的收益门槛。第一策略在T21/T36必须给出具体政策值，并在实验结果出来前登记；没有具体政策不能进入发布验证。

可自动发布仅限在所有者预先授权的版本化政策内，通过完整评估后执行。Agent提案不是发布授权。

## 8. 发布演练场景

演练包缺文件、hash不一致、模型schema不符、Prompt版本错配、供应商超时、数据库冲突、切换中Worker返回、回滚包加载失败。

期望：旧健康版本保持有效或明确停止新增风险；无混合新旧输出；已有成交继续准确记录；所有状态可追踪。

## 9. 运维与安全验收

- PostgreSQL恢复到指定时点，重算账户并与恢复水位对账。
- Worker丢心跳后，旧Worker恢复不得覆盖新结果。
- 外部网页中的指令不能变成工具授权。
- 用户配置的URL不能访问内网或云元数据端点。
- 日志、导出、异常、浏览器bundle中无密钥。
- 临时签名对象URL受权限及过期控制。
- 生产旧定时任务已停，新旧系统无并发写账户。

## 10. 证据包

每次阶段验收生成目录，至少包含：

`manifest.json`：设计revision、代码commit、依赖锁hash、数据hash、模型/Agent/release版本、运行环境、时间、操作者类型、状态。

`results.json`：每个AC通过/失败/未执行/不适用及原因；失败不被汇总数字吞掉。

`report.md`：用户可理解结果、主要限制、复现入口。

`artifacts/`：必要脱敏trace、账本对账、截图、模型指标。

付费真实集成必须在本地关键合同通过后执行，并限定账户、任务数、预算和剩余验证问题。单次成功不能证明全市场、所有周期、所有Agent都可靠。

## 11. 文档与架构维护

CI检查文档链接、schema生成漂移、禁止依赖方向、不可变版本被覆盖、过期兼容点。旧文件巨大不直接判错，但职责跨界和循环依赖必须解决。

新增需求必须能关联目标、对象、任务、AC；没有关联的功能默认暂不进入主版本。修改核心规则需同步设计、schema与相关验收，不再积累只写在聊天和大段工程指南中的特例。
