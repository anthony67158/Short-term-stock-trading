# QMT 理念驱动的三阶段升级方案

> 状态：历史设计记录。2026-08-25 起，多策略治理、路由、版本晋级与委员会已从生产系统移除；相关章节仅用于说明演进背景，不得作为当前实现依据。
>
> 范围：短线操盘台全链路升级方案，不接入 QMT，不连接券商，不自动下单。
>
> 核心约束：保持“AI 交易决策 + 量化预测 + 纪律执行工作台”的产品定位，交易仍由用户在券商端确认和执行。

## 一、执行摘要

QMT 最值得借鉴的不是某个均线、网格或算法名称，而是五个系统原则：

1. 信号、目标仓位、执行、成交反馈分层。
2. 逐 K 线、行情事件、定时任务按场景驱动。
3. 研究、回测、仿真和生产使用同一量化数据口径。
4. 交易成本、滑点、涨跌停、T+1 和容量进入执行评价。
5. 每个模型、委托意图、成交和绩效都可追溯到版本。

当前系统已经具备证据快照、日线与分钟模型、A 股含费回测、嵌套
Walk-forward、目标仓位、T+1、两段式确认、真实成交学习和 Harness。
真正的主要缺口不是“规则太少”，而是：

- LLM 仍直接生成方向、价格和手数，再由代码纠偏；确定性计算的位置不够靠前。
- 今日决策、个股军师、组合分析和预警各有市场状态与规则，存在口径分叉。
- 组合执行计划没有完整计入手续费、滑点、流动性容量和不可成交风险。
- 人工成交前缺少版本化的执行意图状态，成交关联仍有推断成分。
- 模型发布、OSS 并发写、交易日历和普通预警新鲜度存在治理风险。

因此三次升级按以下顺序实施：

| 升级 | 主题 | 结果 |
|---|---|---|
| 第一次 | 统一决策内核 | 兼容现有建议链，新增唯一、确定性、可审计的决策计划 |
| 第二次 | 军师证据链与候选评分 | 综合量化、资金、行情与信息面，不设置独立策略限制 |
| 第三次 | 人工执行与真实学习 | 把目标仓位转成可操作的分批计划，并用真实成交校准建议 |

### 第一次升级实施记录（2026-08-22）

已落地：

- `market-regime.v1`：今日决策、军师和组合分析统一使用
  `TREND_STRONG / RANGE / TRANSITION / RISK_OFF / UNKNOWN`。
- `decision-plan.v2`：把旧建议适配成结构化动作、目标仓位、
  风险预算、含费金额、有效期和阻断原因。
- 买入/加仓由当前证据、价格、账户与风险条件共同校验；减仓和止损仍按风险优先。
- 买入手数按 `0.6%` 默认单笔风险预算、止损距离、现金、单票上限、
  市场总仓位、手续费和 5 bps 滑点共同裁剪。
- 组合执行计划按卖出净到账、买入含费支出重新分配资金，不再用裸成交额
  冒充可用现金。
- LLM 仅提供候选草案；服务端编译最终计划。首次 LLM 失败时返回无交易数字的
  确定性等待计划，已有计划时继续保留上一版。
- OSS 权威账号快照使用原子锁并在锁内复核 ETag，阻止多 FC 实例基于同一旧版本互相覆盖；不使用 OSS `PutObject` 不支持的 `If-Match`。
- 模型、元数据、信号头和事件标签写入不可变 `run-id` 目录，校验 SHA-256 后
  最后切换 manifest。
- 普通预警与云端预警只接受北京时间当日行情；交易日历超出维护范围时自动任务
  失败关闭。
- 灾难性强止损不再等待普通观察窗口或 LLM 确认。
- Advice Harness 新增 `decision-plan.v2` 的费用和动作一致性门禁。

明确留到后续：

- 通用事件编排器、人工执行状态机、TWAP/VWAP 参考和真实滑点归因属于第三次升级。

## 二、不改变的产品目标

### 2.1 保持

- 面向个人 A 股短线、持仓管理和做 T。
- 先给结论和操作，再展示证据与解释。
- AI 帮助用户想清楚，规则帮助用户守纪律。
- 所有交易仍在券商客户端由用户确认。
- 现有四个主工作区保持不变，不新增“量化终端”式主导航。
- 36 维生产 OHLCV 模型口径保持不变；新增模型必须独立版本、独立路径。
- 所有自动化副作用只允许测试账号，生产账号仅做只读验收。

### 2.2 不做

- 不接 `xtquant`、不保存券商账号、不发送真实委托。
- 不把“确认提醒”包装成“已报单”或“已成交”。
- 不因 QMT 支持期货、期权、套利而扩张到 CTA、ETF 申赎或多腿套利。
- 不直接照搬可转债 T+0 网格到 A 股 T+1。
- 不采用文档中未经官方验证的延迟、成本节省或“A 股 80% 时间震荡”等宣传性数字。
- 不用 LLM 替代现金、仓位、价格、交易规则和风险计算。

## 三、QMT 思想的取舍

### 3.1 直接采用

| QMT 思想 | 本系统映射 |
|---|---|
| 逐 K 线驱动 | 日线收盘、完整 5 分钟 K 线事件 |
| 行情事件驱动 | 前台报价轮询和云端盯盘产生标准化市场事件 |
| 定时任务 | 盘前、盘中、收盘、复盘和模型评价任务 |
| 信号与执行分离 | 策略信号 -> 目标仓位 -> 人工执行计划 |
| 目标持仓 | 组合风险预算和单票目标权重的唯一真相 |
| 回测与实盘同策略 | 同一 StrategySpec 和决策编译规则用于回放与线上 |
| 成本与滑点 | 含费、点差、参与率、容量敏感性进入回测与计划 |
| 委托状态 | 改造成“人工执行意图状态”，不冒充券商状态 |
| TWAP/VWAP/冰山 | 改造成大额人工分批建议，不自动报单 |

### 3.2 条件采用

- 趋势跟踪：适合强势、扩散和波动可承受的市场状态。
- 均值回归：只用于震荡状态和有底仓做 T，禁止在单边下跌中摊平。
- 动量与多因子：用于候选排序，不直接等同于买入。
- 网格：只作为已有底仓或高流动性 ETF 的实验性分批计划。
- ATR：用于止损距离和风险归一化，不单独决定方向。

### 3.3 暂不采用

- 统计套利、ETF 申赎套利、可转债转股套利。
- 期货 CTA、保证金、杠杆、多空和换月。
- 盘口冰山真实执行和交易所拆单。

这些能力需要多资产、做空、Level-2、真实委托回报或券商连接，会改变当前产品边界。

## 四、当前基线与风险

### 4.1 已有基础

- `shared/strategySpec.js` 已有版本化的单一日频策略定义。
- `qlib-service/strategy_portfolio_backtest.py` 已覆盖现金、整手、T+1、
  涨跌停拒单、固定滑点和 A 股费率。
- `qlib-service/strategy_nested_walk_forward.py` 已支持净化的嵌套
  Walk-forward 和指数超额比较。
- `shared/evidenceSnapshot.js` 已能记录数据来源、时点、账户版本和模型版本。
- `shared/portfolioAnalysis.js` 已能把目标权重换算成整手执行清单。
- `shared/portfolioRiskPolicy.js` 已有总仓位、现金、单票、行业和弱市闸门。
- `shared/decisionLedger.js` 与 `shared/realOutcomeLearning.js` 已形成建议、
  人工成交和费后结果的基础闭环。
- `harness/` 已覆盖证据、建议、确认、组合和板块的离线质量门禁。

### 4.2 必须先处理的风险

| 级别 | 风险 | 影响 |
|---|---|---|
| P0 | 当前完整股票池策略嵌套 Walk-forward 为 `REJECT` | 不可把现策略宣传或晋级为可靠执行策略 |
| P0 | 主军师建议没有强绑定 StrategySpec 晋级状态 | 真实结果无法归因到可复现策略 |
| P0 | 自动重训可直接覆盖生产模型文件，与人工发布规范不一致 | 模型和元数据可能短暂错配，回滚困难 |
| P0 | OSS `current.json` 版本检查与写入不是原子 CAS | 多设备或多 FC 实例仍可能覆盖有效数据 |
| P1 | 组合买入预算未完整预留费用和滑点 | 可能多算一手，执行后现金为负 |
| P1 | 普通预警第一阶段不校验 `tradeDate` | 昨日价格可能触发弱提醒 |
| P1 | 交易日历只硬编码 2026 年节假日 | 进入 2027 年后定时任务可能误触发 |
| P1 | 日线、盘中和组合市场状态由不同规则计算 | 同一时点可能出现多个结论 |
| P2 | 策略回测仅支持日频多头、等权和固定退出 | 无法证明趋势、回归和多因子策略的独立价值 |
| P2 | 固定 bps 滑点，没有容量与冲击模型 | 回测收益对资金规模不敏感，不够真实 |

### 4.3 当前量化事实

- 生产 36 维模型留出 AUC 约 `0.6521`，可继续作为一个概率信号。
- V2.1 盘中双头最好平衡准确率约 `53.92% / 54.58%`，未过 `58%` 门槛，
  必须继续保持实验标识。
- 当前策略嵌套 Walk-forward 复合收益约 `-1.19%`，4 个外层 fold 中仅
  2 个为正，对沪深 300 复合超额约 `-1.82%`，维持 `REJECT`。
- 第一轮 Tushare 盘后资金流对 V2.1 没有带来稳定增量，不能继续堆同类特征。

升级成功的定义包括“诚实拒绝无效策略”，不要求每个候选都必须晋级。

## 五、目标架构

```text
行情/公告/资金/量化/账户 Adapter
              |
              v
      Evidence Hub
  统一时点、来源、质量和复权
              |
              v
       Market Event
  日线 / 5分钟 / 价格 / 账户 / 定时
              |
              v
       Strategy Engine
  多个独立、版本化、可回测信号
              |
              v
       Portfolio Engine
  市场状态、风险预算、目标仓位
              |
              v
      Decision Compiler
  价格、手数、费用、T+1、失效条件
              |
       +------+------+
       |             |
       v             v
  Advisor Narrator   Execution Planner
  解释与软证据       人工执行与分批计划
       |             |
       +------+------+
              v
      Decision / Fill Ledger
              |
              v
   真实费后复盘、归因、策略治理
```

### 5.1 深化机会

#### 1. Decision Kernel 模块

- 文件：`api/ai.js`、`api/_ai_prompts.js`、`shared/adviceValidation.js`、
  `shared/portfolioRiskPolicy.js`、`shared/portfolioAnalysis.js`。
- 问题：方向、价格、手数和风险分散在 Prompt、校正函数和组合分析中。
- 方案：新增一个深模块，只暴露 `compileDecision(context)` 接口。
- 收益：调用方只需提供标准证据；数值、限制、优先级和降级原因集中，提升
  locality；同一接口可被页面、预警、回测和 Harness 复用，提升 leverage。

#### 2. Evidence Hub 模块

- 文件：`api/_lib.js`、`api/_market_data.js`、`api/ai.js`、
  `shared/evidenceSnapshot.js`。
- 问题：数据抓取、回退、时效判断和证据快照仍分散在大型文件。
- 方案：以统一 `EvidenceBundle` 接口隐藏来源 Adapter，输出来源、`dataAsOf`、
  `observedAt`、复权口径、质量和冲突状态。
- 收益：新增数据源无需修改所有调用方；数据错误可集中回放和测试。

#### 3. Event Orchestrator 模块

- 文件：`src/App.jsx`、`src/alertStore.js`、`api/cron_alert.js`、
  `api/cron_advice.js`、`api/_advice_timer.js`、`s.yaml`。
- 问题：前台轮询、FC Timer、5 分钟任务和账户变更没有统一事件语义。
- 方案：建立标准 `MarketEvent` 和幂等键，按事件类型路由确定性计算。
- 收益：刷新频率、重试、去重和 LLM 调用策略集中，避免重复生成。

#### 4. Strategy Lifecycle 模块

- 文件：`shared/strategySpec.js`、`qlib-service/strategy_contract.py`、
  `qlib-service/strategy_*walk_forward.py`、`shared/strategyPromotionGate.js`。
- 问题：策略定义、回测、生产建议和模型发布不是同一条晋级链。
- 方案：StrategySpec v2、不可变产物、影子记录和人工发布共享同一版本。
- 收益：任何线上建议都能回答“哪个策略、哪个模型、哪个数据版本产生”。

#### 5. Execution Ledger 模块

- 文件：`shared/decisionLedger.js`、`src/planStore.js`、
  `shared/portfolioAccounting.js`、`src/components/PortfolioExecutionPlan.jsx`。
- 问题：建议后直接记录人工成交，缺少执行意图、分批和失效状态。
- 方案：在建议与成交之间增加人工执行计划及状态。
- 收益：能区分“策略错、执行差、没有执行、部分执行”，提高真实学习质量。

## 六、第一次升级：统一决策内核

### 6.1 目标

不增加独立策略层，也不一次性重写现有任务调度。把现有能力收束成一条
唯一、确定性优先的决策链：

```text
证据 -> 市场状态 -> 军师判断 -> 风险预算 -> 目标仓位
     -> 交易计划 -> AI 解释 -> 到价确认 -> 人工执行
```

### 6.2 交付任务

#### Task 1：定义 `decision-plan.v2`

字段至少包含：

```text
decisionId / accountRevision / code
asOf / validUntil / recomputeOn
marketRegime / modelVersions
action enum / currentWeightPct / targetWeightPct / deltaLots
referencePrice / stop / target / maxLossAmount / feeEstimate
trigger / invalidation / evidenceIds / blockedReasons
executionStyle / explanation
```

- 新决策只允许兼容 Adapter 从旧建议文案读取一次动作和手数；进入
  `decision-plan.v2` 后禁止再从文案反推。
- 旧建议只读兼容，新增数据双写 v2，不原地破坏账号快照。
- `decisionId` 对证据、账户版本和参数做稳定指纹。
- `actionability` 明确区分 `READY / BLOCKED / WATCH`。
- 新增风险只受证据完整性、价格合法性、账户约束和硬风控限制。

验收：

- 所有风险增加动作都有目标仓位、最大损失、费用估算、止损和有效期。
- 动作、手数、费用、目标仓位和可执行等级由代码生成；第一阶段允许 LLM
  提供候选价格，最终价格必须经过确定性价带、盈亏关系和风险校验。
- Harness 能拒绝未知枚举、非有限数、证据越权和版本不一致。

#### Task 2：统一市场状态

第一版只使用确定性规则，输出：

- `TREND_STRONG`
- `RANGE`
- `RISK_OFF`
- `TRANSITION`
- `UNKNOWN`

输入包含指数趋势、涨跌扩散、涨跌停结构、成交额、板块扩散和波动。
今日决策、军师、组合分析、板块前瞻和复盘只读同一结果。

验收：

- 同一证据快照在所有入口得到完全相同的状态与风险系数。
- 数据不足输出 `UNKNOWN`，风险增加动作自动降级。
- 状态阈值版本化并进入证据快照。

#### Task 3：建立确定性风险预算与仓位算法

推荐默认口径：

- 单笔计划最大亏损：账户总资产 `0.6%`。
- 高置信时上限：`1.0%`。
- 单票目标权重上限：`20%`，已有规则的 `25%` 作为绝对硬顶。
- 单一行业目标权重上限：`30%`。
- `RISK_OFF` 新增风险上限：账户 `5%` 试错仓，且需双确认。
- 总仓位由市场状态给区间，不由 LLM 自报。
- 手数按 `风险金额 / (入场价 - 止损价)` 与现金、整手、费用共同取最小值。

验收：

- 买入预算预留佣金和过户费。
- 卖出金额展示扣税费后的净到账。
- T+1、涨跌停、停牌、现金和集中度在计划生成前生效。
- 相同输入产生完全相同的手数和目标仓位。

#### Task 4：重构军师职责

军师从“直接决定最终交易数字”改为：

1. 解释确定性计划。
2. 总结公告、新闻和行业等软证据。
3. 指出反方观点和失效路径。
4. 当软证据冲突时给出不确定性说明。

第一次升级采用渐进迁移：

- LLM 继续输出兼容旧界面的候选动作与价位。
- Decision Compiler 以账户、行情、证据和费用口径生成最终计划。
- 页面、预警和决策日志优先消费最终计划。

`judge` 只处理软性时机确认：

- 不得批准已被风险内核阻止的买入。
- 不得延迟灾难性硬止损。
- 不得修改手数、目标仓位和合法价带。
- 失败时回退确定性结论。

验收：

- 删除新链路中对“加仓 2 手”等文案的正则纠偏依赖。
- AI 输出为空、超时或 JSON 损坏时，仍能展示完整可执行的规则计划。
- 自动复核仅在证据实质变化时调用 LLM。

#### Task 5：修复四个基础治理问题

1. 模型发布改为不可变 `runId/` 目录 + checksum manifest 原子切换。
2. 模型冠军仍可在客观训练门禁通过后自动切换 manifest。
3. OSS 账户关键写入增加条件写/租约或事件日志，避免读后覆盖。
4. 交易日历改为可更新数据源，静态表只做明确过期的兜底。

同时修复：

- 普通预警在第一阶段校验交易日和报价新鲜度。
- 组合计划与单股计划统一调用含费执行评估。

验收：

- 模型文件与元数据永不出现混合版本。
- 并发设备写入不会静默覆盖交易事件。
- 过期日历和过期报价不能产生强弱提醒。

#### Task 6：调整界面

### 8.1 目标

在不连接券商的前提下，把 QMT 的执行层思想改造成“可确认、可分批、可记录、
可归因”的人工执行工作流。

### 8.2 交付任务

#### Task 1：`execution-plan.v1`

人工执行意图状态：

```text
DRAFT -> ARMED -> ALERTED -> USER_CONFIRMED
      -> PARTIALLY_RECORDED -> COMPLETED
      -> CANCELED / EXPIRED
```

含义：

- `USER_CONFIRMED` 只表示用户确认计划，不表示已下单。
- `PARTIALLY_RECORDED/COMPLETED` 只由用户录入的真实成交推进。
- 计划绑定 `decisionId`、账户版本、证据时点和有效期。
- 账户或行情实质变化后旧计划自动过期并重算。

#### Task 2：执行方式选择

系统根据交易金额、流动性、时间窗口和紧迫度选择：

| 执行方式 | 使用条件 | 输出 |
|---|---|---|
| 单笔限价 | 小额、流动性足、冲击可忽略 | 一次操作价和失效时间 |
| 分批执行 | 金额较大或位置不确定 | 2-4 批数量、价格和条件 |
| 时间均分参考 | 必须在时间窗内完成 | 类 TWAP 的人工时间表 |
| 跟量参考 | 成交活跃度变化明显 | 类 VWAP 的参与率和上限 |
| 隐蔽分批参考 | 大额但不紧急 | 类冰山的随机批次建议 |

只有具备可靠分钟成交量曲线时才展示“VWAP 参考”；否则降级为普通分批，不冒充
真实 VWAP 算法。

#### Task 3：做 T 与网格实验

仅允许：

- 用户已有可卖底仓。
- 市场状态为 `RANGE`。
- 个股流动性、ATR 和振幅达到门槛。
- 每一腿计入费用、价差和 T+1。
- 设置当日最大次数、最大净买入、最晚复原时间和总仓上限。

单边趋势、跌停风险、重大利空、成交量不足或无可卖底仓时自动禁用。

#### Task 4：事件驱动刷新

标准事件和建议频率：

| 事件 | 触发 | 执行动作 |
|---|---|---|
| `QUOTE_UPDATE` | 前台 15-20 秒、后台约 60 秒 | 只更新价格和确定性触发 |
| `BAR_5M_CLOSED` | 完整 5 分钟 bar 后 | 更新盘中指标、状态和计划 |
| `PRICE_TRIGGERED` | 触及计划价 | 进入观察或硬风险处理 |
| `ACCOUNT_CHANGED` | 人工成交或云同步 | 立即重算仓位、T+1 和计划 |
| `NEWS_MATERIAL` | 可靠公告或重大事件 | 标记旧计划待复核 |
| `DAILY_CLOSE` | 收盘数据完整后 | 结算、复盘、策略评价 |
| `SCHEDULED_REVIEW` | 盘前/午间/收盘 | 只复核到期或变化对象 |

原则：

- 行情事件只运行确定性代码，不逐 tick 调 LLM。
- LLM 只在证据实质变化、计划冲突或用户主动请求时运行。
- 每个事件有幂等键、来源时点、处理版本和重试状态。
- FC Timer 继续作为触发 Adapter，未来可替换成长连接采集器而不修改决策内核。

#### Task 5：成交和滑点归因

用户录入每一笔真实成交后计算：

- 相对建议参考价的决策滑点。
- 相对触发时价格的执行滑点。
- 相对当时 VWAP 的执行偏差。
- 手续费、税费和总交易成本。
- 未执行、部分执行、延迟执行和计划外执行。
- 策略收益、时机收益和执行损耗。

结果按策略、市场状态、动作、股票和执行方式聚合。只有真实费后已平仓结果能调整
风险预算。

#### Task 6：账户级风控

新增确定性账户控制：

- 当日最大已实现亏损。
- 当日最大总资产回撤。
- 连续亏损冷却。
- 单票、行业和相关概念合并暴露。
- 计划中未完成买入占用现金。
- 计划中未完成卖出不提前释放现金。
- 风险事件触发后只允许减仓，不允许新增风险。

#### Task 7：执行界面

在“持仓执行”顶部增加唯一动作队列：

- 今天必须处理。
- 等待条件。
- 受 T+1 阻止。
- 已确认待记录。
- 已完成/已过期。

每条只展示动作、手数、净金额、触发、失效、有效期和执行方式。详细证据与 AI
解释按需展开，避免卡片套卡片。

### 8.3 第三次升级的门禁

- 系统中任何“完成”状态都有真实人工成交记录。
- 重复事件不会重复创建计划或重复记账。
- 账户版本变化会使旧计划失效，不能静默沿用旧手数。
- 分批计划所有批次合计不超过目标手数和风险预算。
- 费用、滑点、部分执行后重新计算现金和仓位。
- 前台触发延迟目标不高于一个轮询周期；后台强提醒不高于 75 秒。
- LLM 调用次数相对固定频率刷新显著下降，并记录节省比例。

完成标志：

> 系统能够区分策略判断、计划编译、用户执行和真实成交，并量化每一层对最终费后

## 十、统一风险口径

建议把风险优先级固定为：

```text
数据有效性
  > 账户与 T+1
  > 灾难性止损
  > 总仓位/现金/集中度
  > 策略适用状态
  > 盈亏比与目标仓位
  > LLM 软证据
```

止损拆成两类：

- 硬风险止损：跌停风险、重大利空、收盘有效破位、超出最大亏损。不得等待 LLM。
- 软结构失效：盘中插针、短时跌破 VWAP、弱动量。进入两段式观察。

这保留现有“防插针”体验，同时避免所有止损都等待至少 90 秒。

## 十五、最终产品形态

升级完成后，用户看到的仍然是“短线操盘台”，不是 QMT 克隆：

- 今日决策告诉用户现在属于什么市场、哪些证据支持操作、最多承担多少风险。
- 持仓执行告诉用户目标仓位和下一步动作，而不是堆砌指标。
- 到价后系统用最新证据确认，硬风险不等待，软信号防插针。
- 大额操作给人工分批节奏，小额操作保持简单。
- 用户在券商完成交易后回填真实成交，系统计算费后收益和执行偏差。
- 每一次建议都能追溯到证据、模型、风险预算、执行和结果。

这才是对 QMT 设计理念最有价值的迁移：不改变产品边界，却把“研究、决策、
纪律、执行、复盘”收束成同一条可验证链路。
